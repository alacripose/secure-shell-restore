Secure Shell next-version development plan
The primary repository is alacripose/secure-shell. I located its existing audit, architecture, decisions, implementation plan, and agent conventions.

The most important finding is that this cannot be approached as an ordinary renderer upgrade. The existing project already has explicit architectural decisions that the next version needs to revisit rather than accidentally inherit.

1. Existing audit findings
Audit located docs/FORMAT-SOURCES-AUDIT.md

The existing 1,180-line audit contains several findings directly relevant to your requested direction.

Existing finding

Consequence for the next version

OpenLock has multiple independently evolved package formats.

Preserve its working shell and display conventions without inheriting every package format.

planet-package has its own package framing, magic, and version grammar.

Do not make it the permanent Secure Shell package dependency.

OpenLock's package-envelope implementation has incomplete signing evidence.

Design a separately verifiable package provenance and signature system.

OpenLock uses MongoDB for its axis-witness comparison workflow.

Its three-reading verification pattern is worth studying, but its unauthenticated local store should not be copied as-is.

The SWF/API tooling and shell development drifted apart.

Make API tooling and the user-visible shell part of the same witnessed development process.

Generated shell assets became substantially larger than their source declarations.

Preserve generated-versus-authored boundaries and automate regeneration.

The existing CUA/control relationship is not fully implemented in Secure Shell.

Make the CUA driver an actual bounded control and verification mechanism, not a screenshot generator.

There is an important architectural conflict to resolve.

The current Secure Shell AGENTS.md explicitly rules out MongoDB, new package formats, and additional signature schemes. Its architecture uses a Debian backend, an append-only ledger, SHA-256 hashing, and Ed25519 checkpoints.

Your requested next version proposes a different direction: a MongoDB-backed server store, BLAKE3-based package integrity, signed package streaming, and a CUA-driven desktop. Those are legitimate proposals, but they must be explicitly recorded as superseding decisions rather than quietly implemented underneath the existing rules.

The most important findings
The SWF importer really is tied to the legacy crate family. Its current manifest directly depends on planet-aead, planet-package, and planet-shell-ledger, with planet-client in development tests. It still emits the V4PKG001 frame through planet-package. The newer hashed format identifier work does not, by itself, replace that frame.

Secure Shell's current rules conflict with the requested v2 direction. The existing architecture explicitly rejects MongoDB and new package formats. The plan therefore makes a superseding owner decision its first milestone, rather than quietly building around those restrictions.

BLAKE3 and signing are separate responsibilities. The documents use BLAKE3 for package content identity and leave the public-key signature suite as an explicit decision. A hash is not a signature or an authorization verdict.

The civilian system is not yet the completed cellular CUA architecture. The repositories show meaningful System-1 and persistence work, but the rechecked specification identifies the full cellular learning system and lived verification as unfinished. The new acceptance document preserves that distinction.

The 20 questions were shown in the middle of the work and are also preserved in the implementation plan. Unanswered questions remain open rather than becoming hidden assumptions.

Important architectural changes
1. Restore is the first release.

The implementation sequence now begins with OpenLock generation, followed by Debian database reconstruction, MongoDB-backed package admission, and the first streamed TUI desktop containing the taskbar and actual Debian console.

2. Qt 6 is the product client.

I checked Qt's official release information. Qt 6.12.0 LTS, released September 30, 2026, is the current baseline. The plan specifies pinning its exact version through GitHub CI, rather than using floating dependencies.

3. The SWF importer is no longer the runtime foundation.

The audit now distinguishes the pre-split and post-split package families, the five observed package magics, and the corrected 129-identifier classification.

It records the actual planet-* dependency lock-in and a migration route through quarantined compatibility readers.

4. The CUA system becomes a much larger undertaking.

The revised acceptance specification includes persistent System-1 agents, privileged host-operation brokers, air-gapped management, thousands of worker targets, cellular learning, and a 24-hour continuous simulation.

It also uses the realtime simulation transcript accurately: particularly its observations about scene persistence, physics, motion, audio, multiple actors, and the failures of generative simulations. Those failures become test requirements rather than assumed capabilities.

5. The agent API becomes an independently provisioned system.

Agents can request small API templates, windows, packages, dependencies, and training work without mounting the entire desktop. The health ratchet automatically generates convention proposals, while actual rule changes remain ticketed and authorized.

Decisions deliberately left open
I preserved the unanswered technical details rather than inventing them. These include the exact package identifier grammar, key custody and rotation, receipt schema, MongoDB replication, stream cryptographic profile, Qt XML grammar, kernel capability catalogue, and exact performance budgets.

The cryptographic proposal separates BLAKE3 content identity, authenticated encryption, and Debian-server signing. They are not treated as interchangeable mechanisms.

One important distinction: these five files are local deliverables, not commits to your GitHub repositories. The next implementation stage should begin by recording the Restore superseding decisions and opening the first ticketed OpenLock generation work.
